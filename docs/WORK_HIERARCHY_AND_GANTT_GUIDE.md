# Work Hierarchy and Gantt Planning Guide

## Purpose

This guide defines how governed delivery work should support editable hierarchy, configurable exports, dependencies, and Gantt-style timeline planning.

The key principle:

```text
Generate work with a generic governance hierarchy first.
Then adapt it to the organization's actual work-management configuration.
```

Different organizations configure Jira, ADO, Rally, and Asana differently. Some use initiatives and epics. Some only allow stories and tasks. Some disable subtasks. Some use custom issue types. The engine should not assume one universal hierarchy.

## Why This Matters

A generated ticket package is only useful if it can fit the organization's actual system.

Bad assumption:

```text
Initiative → Epic → Story → Task → Sub-task always works.
```

Better assumption:

```text
The engine should understand hierarchy conceptually, then map or flatten based on the target org's configuration.
```

## Core Concepts

| Concept | Meaning |
|---|---|
| Conceptual hierarchy | The ideal governance structure generated by the agent. |
| Platform hierarchy | What Jira, ADO, Rally, Asana, or another tool supports. |
| Export hierarchy | The flattened or transformed hierarchy used for import/export. |
| Dependency graph | Schedule, control, and sequencing relationships between work items. |
| Gantt plan | Timeline view using duration, dependency, owner, and launch-blocking metadata. |

## Recommended Conceptual Hierarchy

The agent may generate work conceptually as:

```text
Program / Initiative
→ Epic / Capability
→ Story / Deliverable
→ Task / Control Work
→ Sub-task / Execution Step
```

But this must remain editable.

## Editable Hierarchy Profiles

Hierarchy configuration files live here:

```text
configs/work_hierarchies/
```

Current presets:

| Config | Purpose |
|---|---|
| `jira_default.json` | Supports initiative, epic, story, task, and sub-task. |
| `story_task_only.json` | Minimal hierarchy for orgs that only support stories and tasks. |

## Example: Jira Default

```text
Initiative → Epic → Story / Task → Sub-task
```

Use this when the Jira site supports initiatives or Advanced Roadmaps-style hierarchy.

## Example: Story/Task Only

```text
Story → Task
```

Use this when the org does not support initiatives, epics, or subtasks.

In this case, the engine should preserve the original conceptual hierarchy in metadata, while exporting only supported work item types.

## Flattening Strategy

When an org does not support the generated level, choose one of these strategies:

| Strategy | Meaning |
|---|---|
| `flatten_to_parent` | Move unsupported items into their nearest supported parent. |
| `flatten_to_story` | Convert unsupported hierarchy into story-level work. |
| `convert_to_label` | Preserve unsupported type as a label/tag only. |
| `omit` | Do not export unsupported levels. |

Recommended default:

```text
flatten_to_story
```

This keeps the work executable even when the target platform has a limited configuration.

## Dependency Types

Dependencies should be separate from hierarchy.

Hierarchy answers:

```text
What work belongs under what parent?
```

Dependencies answer:

```text
What work must happen before, after, or alongside other work?
```

Recommended dependency types:

| Type | Meaning | Blocks Schedule |
|---|---|---|
| `blocks` | This work blocks another item. | Yes |
| `blocked_by` | This work is blocked by another item. | Yes |
| `must_finish_before` | Finish-to-start Gantt dependency. | Yes |
| `relates_to` | Related but not schedule-blocking. | No |
| `requires_evidence_from` | Depends on evidence from another work item. | Usually Yes |
| `requires_approval_from` | Depends on approval from a review owner. | Yes |

## Recommended Dependency Logic

For governed delivery, the engine should infer dependencies like:

| Work Item | Depends On |
|---|---|
| Production launch approval | Legal, Security, Data Governance, QA evidence, open blockers resolved |
| File delivery test | Destination confirmation, recipient allowlist, route config |
| Dashboard launch | Row-level security validation, access review, refresh validation |
| API launch | Auth review, payload schema, logging review, monitoring plan |
| Data transformation launch | Source field approval, lineage review, test results |

## Gantt Planning

A Gantt view should be separate but connected.

Generated tickets should include enough metadata to support a Gantt view:

| Field | Purpose |
|---|---|
| `duration` | Estimated effort/duration. |
| `start_offset` | Start position relative to project start. |
| `end_offset` | End position relative to project start. |
| `dependencies` | Work that must happen first. |
| `can_parallelize` | Whether item can run alongside others. |
| `owner_role` | Swimlane or resource owner. |
| `launch_blocker` | Whether item is critical to launch. |
| `evidence_required` | Artifacts needed before closure. |

## Gantt Output Formats

The engine should eventually generate:

```text
gantt_plan.json
gantt_plan.md
gantt_plan.mmd
gantt_plan.csv
```

Recommended display formats:

| Format | Use |
|---|---|
| JSON | UI rendering and downstream planning tools. |
| Mermaid Gantt | Quick visual preview in docs. |
| CSV | Excel/Smartsheet/MS Project import. |
| Markdown | Human-readable planning summary. |

## UI Requirements

The UI should allow users to:

1. View generated hierarchy.
2. Change target hierarchy profile.
3. Edit work item type.
4. Drag/drop or re-parent work items.
5. Mark unsupported levels and choose flattening behavior.
6. View dependencies as arrows.
7. Edit dependency type.
8. Toggle Gantt view.
9. Export tickets with dependency and timeline columns.
10. Export Gantt data separately.

|---|---|

| Dependencies | Blocking items. |

## Best Practice vs Pragmatic Workaround

### Best Practice

Use configurable hierarchy profiles and dependency metadata. Export only after validating that target platform supports the requested hierarchy.

### Pragmatic Workaround

When the org's Jira/ADO/Rally/Asana configuration is unknown, export as stories and tasks only, preserve original hierarchy in metadata columns, and include dependency columns for manual import cleanup.
